# 0. 한눈에 보기

**제품 한 줄 정의.** 5~30명 규모 사업장의 관리자가 **사업장 라이선스**(사업 허가·시설 허가·보험)와 **직원 자격**(면허·자격증·보수교육·신원조회)의 만료일과 핵심 정보만 폰에서 관리하고, **만료 1개월·1주·1일 전에 푸시와 이메일로 세 번** 알림을 받고, 실사 때 바로 쓸 수 있는 리포트를 뽑는 앱. 서류는 촬영해 **기기 안에서 정보만 추출한 뒤 원본 이미지를 즉시 파기**하고, 남는 것은 암호화된 데이터뿐이다.

**설계 원칙 5가지**

1. **이미지는 저장하지 않는다(Zeo-image).** 촬영·PDF는 OCR을 위한 일회용 입력이다. 추출이 끝나면 원본 파일·썸네일·캐시를 남기지 않는다.
2. **남는 것은 구조화된 데이터뿐, 그마저 최소로.** 저장하는 개인정보는 **라이선스 유형 / 이름(또는 별칭) / 발급일(시작일) / 만료일 / 발급기관 / (선택) 라이선스 번호** — 이 여섯 항목이 전부다. 주민번호·생년월일·주소·전화번호·건강정보·문서 이미지는 수집하지 않는다. 이 작은 레코드를 SQLCipher로 암호화해 기기에 두고, 필요하면 종단간 암호화로 동기화한다.
3. **원본 증빙은 고객의 몫으로 남긴다.** 앱은 만료일과 보관 위치만 기록한다. 우리 쪽에 사진이 존재한 적이 없으므로 유출될 사진도 없다.
4. **알림은 세 번 온다.** 만료 1개월 전(D-30), 1주 전(D-7), 1일 전(D-1). 푸시 팝업과 이메일을 함께 보내고, 받는 사람(관리자·보유자)을 지정한다. 한 번 놓쳐도 두 번 더 남는 구조가 이 제품의 재방문 이유다.
5. **이미 쓰는 캘린더에 올린다.** 만료일을 Google Calendar에 동기화하면, 관리자는 새 앱을 열지 않아도 되고 캘린더의 이메일·팝업 알림으로 같은 3단계를 다시 받는다. 단, 캘린더에는 **마스킹된 제목과 날짜만** 나간다.

**3줄 요약**

1. 시장은 비어 있지 않다. 개인용 앱(월 $5~7)과 팀용 웹 서비스(월 $15~149)가 여럿 있고, 대부분 **서류 이미지를 서버에 보관한다.** 수요는 검증됐고 1등은 아직 없다.
2. 이기는 방식은 기능을 더 넣는 게 아니라 **"서류를 보관하지 않는다"**는 구조적 차이다. "우리 쪽에는 직원 신분증 사진이 없다"는 문장은 따라 하기 어렵다.
3. 6주 MVP → 4주 파일럿(5~10개 사업장) → 유료 출시. 핵심 지표는 "관리자가 D-30 안에 실제로 갱신을 끝낸 비율"이다.

**이 문서에서 이미 내린 결정(바꾸려면 근거가 필요한 것들)**

| 항목 | 결정 | 이유 |
|---|---|---|

# 1. 프로젝트 개요 & 틈새시장 포지셔닝

## 1.1 문제: "만료일 한 칸"이 만드는 실제 손실

이 사업의 고객은 "관리가 귀찮은 사람"이 아니라 **이미 사고를 당해 본 사람**이다. 실제로 반복되는 실패 장면은 네 가지다.

| 장면 | 무슨 일이 일어나는가 | 비용 |
|---|---|---|
| 주 정부 실사·인스펙션 | 요양보호사 TB 검사 결과가 3주 전 만료. 서류철을 뒤지지만 갱신본이 없음 | 지적사항, 시정 계획, 반복 실사, 최악의 경우 영업 정지 |
| 건설 현장 감사 | OSHA 30시간 이수증이 만료된 인력이 장비를 운전 | 벌금, 보험 클레임 거절, 발주처 계약 해지 |
| 클리닉·살롱 | 위생/면허 갱신 누락으로 해당 직원이 근무 불가 | 급여·교대조 붕괴, 재교육 비용, 예약 취소 |
| 보험·계약 갱신 | 책임보험 증명서(COI)·사업 허가 갱신 누락 | 입찰 자격 상실, 고객사 계약 중단 |

핵심은 **정보가 없는 게 아니라, 한 곳에 모여 있지 않고, 아무도 매일 보지 않는다**는 점이다. 대부분 스프레드시트 + 공유 드라이브 + 서류 캐비닛 + 단톡방으로 운영한다.

그리고 두 번째 문제가 있다. **서류를 한곳에 모으려는 순간, 사진 더미가 생긴다.** 신분증, TB 검사지, 신원조회 보고서가 관리자 개인 폰 사진첩과 클라우드 드라이브에 흩어지고, 그게 이 사업의 가장 큰 위험 자산이 된다. 우리는 이 두 번째 문제를 없애는 쪽을 택한다.

## 1.3 경쟁 지형 (2026년 11월 확인)

| 범주 | 대표 제품 | 가격(확인 시점) | 강점 | 약점 = 우리의 기회 |
|---|---|---|---|---|
| 개인용 앱 | CertKeeper(iOS, 개인용), CertTrack, CerTracker, Certibee 개인 플랜 | $6.99/월·$59.99/년, Certibee 개인 $4.99/월 | 저렴, OCR·만료 알림·PDF 기본 제공 | 1인 사용 전제. 관리자가 직원 20명을 한 화면에서 보는 개념이 없음 |
| 소규모 팀용 웹 SaaS | CertKeeper(웹), HRDocket, Certibee Team, CredTally, LeaveCalc, PunchPro | $19/월(15명), $49/월(25명), $49/월(10명), $4.50/좌석, $15/월(25명, 날짜만), $39.99+$7/인 | 인원 과금, 알림, 컴플라이언스 매트릭스, 리포트 | **직원 서류 파일을 서버에 보관**(예: CertKeeper는 "문서는 암호화 저장" 안내). 웹 대시보드 중심이라 폰 촬영 동선이 약함. 제로지식·무저장 설계를 내세우는 곳이 없음 |
| 엔터프라이즈 HR/컴플라이언스 | Certemy, 기존 HRIS(ADP·Paycom 등) 자격 모듈, Joint Commission 대응 솔루션 | 수백~수천 달러/월, 도입 컨설팅 별도 | 감사·워크플로 완비, SSO, 통합 | 5~30명 사업장에는 과잉. 도입 3~6개월, 교육 필요 |
| 실사용 현실 | 스프레드시트 + 공유 드라이브 + 카톡/문자 | 무료(인건비 발생) | 익숙함 | 만료를 아무도 매일 보지 않음. 사진이 개인 폰·드라이브에 흩어짐. 감사 때 수작업 |

**해석**

- "빈 시장"이 아니라 **"1등이 아직 없는, 막 포화되기 시작한 시장"**이다. 경쟁자가 있다는 것은 수요 검증이고, 동시에 **차별화 없이는 6개월 안에 가격 경쟁에 휩쓸린다**는 뜻이다.
- 경쟁 제품 대부분이 **서류 보관함**을 팔고 있다. 그들은 사진을 받아 저장하고, 암호화와 접근제어로 위험을 관리한다. 우리는 **애초에 갖지 않는 것**으로 같은 위험을 없앤다. 이건 기능 차이가 아니라 **책임의 크기 차이**이고, 그래서 영업에서 가장 강한 문장이 된다.

## 1.4 포지셔닝

두 축으로 본다. 가로축 = **팀 규모/운영 부담**, 세로축 = **보관하는 민감정보의 양(적을수록 위쪽)**.

- 개인용 앱: 모바일은 좋지만 팀 관리 기능이 없고, 사진을 기기에 쌓는다.
- 엔터프라이즈: 감사·워크플로는 강하지만 무겁고, 서류 원본을 대량 보관한다.
- 웹 팀 SaaS: 팀 기능은 있지만 폰 촬영 동선이 약하고, 서버에 파일을 보관한다.
- **우리: 5~30명 규모에서, 폰에서 끝나고, 서류 원본을 갖지 않는다.**

한 문장 포지셔닝: **"직원 20명짜리 사업장이 실사 당일 서류철을 뒤지지 않게 만들되, 직원 신분증 사진은 우리 서버에도, 당신 폰에도 남기지 않는 앱."**

## 1.5 차별점 3개와 방어 전략

| 차별점 | 구현 방식 | 왜 따라오기 어려운가(방어력) |
|---|---|---|
| 1) 이미지를 남기지 않는 구조 | 촬영 세션 → 기기 내 OCR → 필드 확인 → 즉시 폐기. 사진첩 저장·서버 업로드·썸네일·캐시 없음 | 경쟁사는 "문서 보관"이 제품의 핵심 가치라 구조를 바꾸면 기존 고객의 자료가 사라진다. 반대로 우리는 나중에 보관 기능을 붙일 수 있지만, 보관하던 쪽이 안 보관으로 전환하기는 어렵다 |
| 2) 최소 수집 + 제로지식 메타데이터 | 저장 항목을 자격 정보로 한정, SQLCipher + 필드 암호화, 서버는 암호문만 | "우리는 사진을 갖지 않는다"는 주장은 감사·계약·보안 설문에서 검증 가능한 사실이다. 말만 베끼면 아키텍처에서 드러난다 |
| 3) 업종별 규제 라이브러리 | 자격 유형마다 유효기간, 근거 규정, 갱신 사이트, 필요 서류, 원본 보관 위치 항목까지 큐레이션(예: 주별 TB 검사 주기, OSHA 30 유효기간) | 콘텐츠 노동 + 지속 갱신. 전환비용(우리 라이브러리에 맞춰 세팅한 데이터)도 방어막 |

추가 방어막: **실사 대응 리포트 표준화**, **전환비용**(직원·자격 이력이 쌓일수록 이사 비용 발생), **업종 협회·보험 대리점 제휴(리셀) 채널**, **낮은 운영비**(파일 저장이 없어 원가가 거의 인원수에 비례하지 않음).

**알림은 차별점이 아니라 기본기다.** 경쟁사도 만료 알림을 보낸다. 다만 우리는 (a) **사업장 라이선스와 직원 자격을 같은 만료 달력**에 놓고, (b) **D-30·D-7·D-1 세 번**을 기본값으로 두고, (c) **푸시와 이메일을 동시에, 받는 사람을 지정**하며, (d) 알림이 가리키는 대상이 **사진이 아니라 숫자(날짜)** 라는 점이 다르다. 알림 문구에 민감한 정보가 실릴 이유가 없다.

## 1.6 이 제품이 되지 말아야 할 것

- 급여·근태·스케줄링까지 넓히는 것(PunchPro 같은 복합 제품과 정면 충돌, 유지비 폭발).
- 강의(CEU) 판매 중개(별도 사업, 규제 이슈).
- "AI가 규정을 판단해 준다"는 약속(책임 소재 문제, 오답 시 신뢰 붕괴). OCR로 **날짜 후보를 제안**하는 선에서 멈춘다.
- **클라우드 문서 보관함으로 회귀하는 것.** 편의 요청이 많겠지만, 그 순간 이 제품의 유일한 구조적 차별점이 사라진다. 원본이 필요하면 고객의 저장소로 내보내는 방식으로 대응한다(2.9).

# 2. 핵심 보안 & 암호화 설계 (이미지 무저장 구조)

> 사용자 요구의 핵심 변화: **"이미지는 저장하지 말고, 데이터만 관리"**. 이 장은 그 결정을 아키텍처·UX·계약 문구까지 일관되게 옮긴 것이다.

## 2.1 이 결정이 바꾸는 것

| 항목 | 이미지 보관형(경쟁사 다수) | 우리(무저장) |
|---|---|---|
| 유출 시 최악의 경우 | 직원 신분증·검사 결과 사진이 그대로 노출 | "누가 어떤 자격을 언제까지 갖고 있는가" 수준의 6개 필드만 노출 |
| 유출 대응 비용 | 사진 포렌식, 통지 범위 산정, 규제 신고 검토 | 레코드 단위 통지·비밀번호 재설정 수준 |
| 저장 비용 | 문서 1건당 수 MB × 직원 수 × 버전 | 직원 1명당 수 KB. 사실상 0에 가까움 |
| 사고의 **원인** 제거 | 저장·암호화·접근제어로 위험을 **관리** | 위험의 원천(사진)을 **만들지 않음** |
| 감사 대응력 | 앱 안에서 원본 제시 가능 | 원본은 고객 저장소에 있고, 앱은 위치·날짜를 지시 |

정직하게 말해야 할 부분: **원본 증빙을 앱에서 바로 보여줄 수는 없다.** 실사관이 "그 자격증 실물(사본)을 보여달라"고 할 때, 앱은 "언제 만료이고, 어디에 보관돼 있는지"를 알려준다. 이 한계를 숨기지 않고, 2.9에서 제품적으로 메운다.

## 2.2 위협 모델(무저장 구조 기준)

| 위협 | 현실적 시나리오 | 대응 |
|---|---|---|
| 기기 분실·도난 | 관리자 폰을 습득한 사람이 앱을 열어봄 | 앱 잠금(생체인증) + DB 암호화 + 백그라운드 스냅샷 가리기 |
| 백업 유출 | iCloud/Google 백업에서 DB 파일 추출 | DB 자체가 암호문, 키는 백업에 포함되지 않도록 `ThisDeviceOnly` |
| Google 계정·캘린더 침해 | 고객의 Google 계정이 털리거나 공유 캘린더가 유출됨 | 사진·SSN·생년월일이 없고, 번호는 암호문. 노출되는 것은 마스킹된 제목·날짜 수준 |
| 내부자(운영자) | 우리 회사 직원이 고객 데이터 열람 | 우리 쪽에 데이터가 없다(서버 없음). 지원은 고객 화면 공유로만 |

| 악성 앱·루팅 기기 | 키로거, 화면 캡처 | 생체인증 게이트, 루팅/탈옥 감지 시 경고·제한 모드, 캡처 차단 |
| **촬영 순간의 잔여물** | 사진첩 자동 저장, 임시파일, OCR 로그, 크래시 덤프 | 카메라 세션 직접 사용, 메모리 버퍼만 사용, 디스크 캐시 금지, 로그에 텍스트·경로 금지 |
| 리포트 유출 | 내보낸 PDF가 이메일로 돌아다님 | 워터마크(수신자·시각·목적), 선택적 마스킹, 내보내기 감사 로그 |
| 캘린더로 정보가 새어나감 | 마스킹 안 된 제목·설명에 면허번호나 직원 실명이 들어가 Google 계정·조직 공유 캘린더에 노출 | 이벤트 제목은 `[갱신] 유형 · 보유자 참조` 형식만, 설명에는 앱 링크 1줄. 연동 전 미리보기로 사용자 확인 |
| 로그·분석 유출 | 크래시 리포터에 직원명·면허번호 실림 | PII 로그 금지 규칙, 분석 이벤트에 식별자 해시만 |

**명시적 비목표**: 국가급 공격자 방어, 기기가 처음부터 장악된 경우, 직원이 자기 휴대폰으로 원본을 찍어 개인적으로 보관하는 행위(이는 앱이 막을 수 없고, 고객 정책의 영역).

## 2.3 최소 데이터 스키마와 데이터 분류

### 저장하는 항목 — 이것이 전부다

| # | 필드 | 필수 | 예시 | 저장 방식 | 알림·캘린더 노출 |
|---|---|---|---|---|---|
| 1 | **라이선스 유형/카테고리** | 필수 | 사업 허가 / 전문 면허 / 보험 / 안전·보수교육 / 시설 허가 | SQLCipher | 노출(민감하지 않음) |

보조 필드(선택, 비워두기 권장): 별칭, 원본 보관 위치 메모(예: "사무실 캐비닛 B"), 메모. 이들은 개인정보가 아니라 업무 메모다.

### 저장하지 않는 항목 — 명시적 금지

- 문서 이미지·PDF·썸네일 (휘발성 OCR 후 폐기)
- 주민등록번호/SSN, 생년월일, 주소, 전화번호, 개인 이메일(직원 본인 계정 제외)
- 건강정보 상세(검사 수치·진단명), 신원조회 보고서 원문
- 서명, 계좌·카드 정보, 사진, 위치

스키마에 이 컬럼들이 **존재하지 않는 것**이 컴플라이언스를 가볍게 만드는 핵심이다. "무엇을 저장하지 않는가"를 개인정보처리방침 첫 문단에 쓴다.

### 데이터 등급

| 등급 | 예시 | 저장 | 서버 전송 | 기본 보존 |
|---|---|---|---|---|
| 0. 원본 파일 | 자격증 사진, PDF 스캔 | **저장 안 함(휘발성)** | 전송 안 함 | 추출 완료 즉시 폐기(수 초) |
| A. 자격 레코드 | 유형, 이름, 발급일, 만료일, 발급기관, (선택) 번호 | SQLCipher(+번호는 필드 암호화) | 암호문만(E2EE) | 계정 존속 + 삭제 요청 시 30일 내 파기 |
| B. 업무 메타데이터 | 별칭, 원본 보관 위치, 메모, 조직·근무지 | SQLCipher | 암호문만 | 동일 |
| C. 계정·운영 | 조직명, 요금제, 초대 이메일, 기기 목록 | DB(암호화) | 필요 최소 항목은 평문 가능 | 계정 존속 |
| D. 진단·통계 | 화면 조회 수, OCR 성공률(문자열 없이) | 비식별 | 집계값만 | 12개월 |

원칙: **0등급은 존재하지 않게 만든다. A·B는 서버가 읽을 수 없어야 한다.** 그리고 A등급 자체가 이미 최소다 — 유출되어도 "누가 어떤 자격을 언제까지 갖고 있다" 수준을 넘지 않는다.

## 2.4 휘발성 OCR 파이프라인(무저장 보장)

| 단계 | 처리 | 보장해야 할 것 |
|---|---|---|
| 1. 캡처 | 카메라 세션에서 프레임을 직접 받아 메모리 버퍼로. `UIImageWriteToSavedPhotosAlbum` 계열 API 사용 금지. 파일 선택(사진첩·PDF)은 보안 스코프로 읽고 복사본을 만들지 않음 | 사진첩에 아무것도 남지 않음 |
| 2. 전처리 | 메모리에서 회전·리사이즈·대비 보정. 디스크 임시파일 금지 | `/tmp`, 캐시 디렉터리에 파일 0건 |
| 3. OCR | 기기 내 엔진(Apple Vision / Google ML Kit). **이미지 바이트는 네트워크로 나가지 않음** | 오프라인에서도 동작 |
| 4. 필드 추출 | 날짜·번호·이름 후보를 규칙 기반으로 뽑아 메모리에만 유지 | 추출 텍스트 임시 저장 금지 |
| 5. 사용자 확인 | 후보 1~3개를 버튼으로 제시. 확정 시에만 **구조화 레코드** 생성 | 자동 확정 금지, 오선택 0건 |
| 6. 폐기 | 버퍼 해제·덮어쓰기(가능한 범위), 세션 종료. 화면 전환 시 프리뷰 제거 | 종료 후 복원 가능한 잔여물 없음 |
| 7. 예외 | 앱이 중간에 죽으면? 임시 데이터는 애초에 디스크에 없으므로 사라짐 | 크래시 리포트에 이미지 첨부 금지 |

**UI에 반드시 노출**: 촬영 화면 상단에 "이 사진은 저장되지 않습니다. 정보만 읽고 바로 삭제합니다." 확인 화면에도 "원본은 이미 삭제되었습니다" 표시. 이 문구가 곧 마케팅이다.

**기술적 함정 체크리스트**
- [ ] 카메라 플러그인이 자동으로 사진첩에 저장하지 않는가(기본값 확인)
- [ ] OS 스크린샷·앱 전환 스냅샷에 촬영 화면이 남지 않는가(`FLAG_SECURE`, iOS 스냅샷 블러)
- [ ] 제3자 OCR SDK가 이미지를 서버로 보내지 않는가(계약·네트워크 로그 확인)
- [ ] 크래시 리포터가 메모리 이미지·OCR 텍스트를 첨부하지 않는가
- [ ] 클립보드에 OCR 텍스트가 복사되지 않는가(붙여넣기 UI 제공 시 경고)
- [ ] 공유 시트로 원본을 내보내는 기능을 넣더라도 앱 내부 저장은 하지 않는가

## 2.5 암호화 아키텍처(메타데이터 중심)

```
[생체인증/패스코드]
   │ (인증 성공 시에만 키 사용 가능)
   ▼
[기기 키스토어]  iOS Keychain(ThisDeviceOnly + biometry) / Android Keystore
   │
   ▼
[마스터 키 MK]  256bit, 기기 밖으로 나가지 않음
   │
   ├─ wrap ─▶ [조직 키 OK]  멤버별 공개키로 래핑
   │                │
   │                ▼
   │          [레코드 DEK]  레코드 묶음(직원 1명)당 256bit
   │                │
   │                ▼
   │          AES-256-GCM(선택 필드: 라이선스 번호)
   │                │
   │                ▼
   │          캘린더 payload(v1.<base64url>)
   │
   └─ key ──▶ [SQLCipher DB 키]  AES-256, 페이지별 HMAC 무결성
```

- **파일 암호화 계층이 통째로 사라졌다.** 저장하는 것이 작은 레코드뿐이라 구조가 단순해지고, 버그 표면과 키 관리 부담이 줄어든다.
- **암호화가 필요한 것은 선택 필드(라이선스 번호)뿐이다.** 캘린더에 들어가는 나머지 5개 필드는 마스킹·최소화로 보호한다(2.8).
- **필드 단위 암호화**: 면허번호·생년월일·검사 결과처럼 민감도가 높은 필드는 레코드 안에서 한 번 더 암호화(검색이 필요 없는 값에 한정). 이름·만료일은 DB 암호화로 충분하지만, 화면 표시용 인덱스는 최소화.
- **암호 알고리즘은 표준만**: AES-256-GCM, HKDF-SHA256, P-256 ECDH. 자체 암호 구현 금지.
- 남는 위험은 "레코드가 유출되면 직원의 자격 보유 사실은 알 수 있다"는 수준이다. 사진이 없으므로 신분증 위조·의료정보 노출 같은 2차 피해가 원천적으로 작다.

## 2.6 기기 내 저장

| 항목 | 구현 | 실패 시 흔한 실수 |
|---|---|---|
| 구조화 데이터 | SQLCipher(AES-256-CBC + 페이지 HMAC). 키는 Keychain/Keystore에서 런타임 주입 | 키를 코드·설정 파일에 하드코딩, 기기 ID로 유도 |
| 민감 필드 | 라이선스 번호(선택)만 AES-256-GCM 필드 암호화 + 마스킹 표시 | 전부 평문 컬럼에 넣고 "DB가 암호화돼 있으니 괜찮다"고 착각 |
| 파일 보호 등급(iOS) | `NSFileProtectionComplete`, 앱 스위처 스냅샷 가리기 | 기본 등급 방치 |
| Android | 파일 기반 암호화(FBE) 전제 + 앱 전용 저장소, `FLAG_SECURE` | 오래된 Jetpack Security Crypto에 의존(지원 중단 계열) |
| 로그 | 이름·면허번호·OCR 텍스트 로그 금지. 릴리스 빌드에서 로그 스트립 | 크래시 리포트에 경로·이름 포함 |
| 클립보드·공유 | 데이터 표 복사 시 경고, 공유는 리포트 PDF만 | 원본 이미지를 메신저로 전송 |

## 2.7 키 관리·생체인증·키 회전

- **최초 실행**: MK 생성 → Keychain/Keystore 저장 → 복구 수단(복구 키 또는 조직 escrow) 선택 요구.
- **잠금**: 앱 진입 시 Face ID/Touch ID/지문, 실패 시 기기 패스코드. 5분 백그라운드 후 재잠금(설정 가능).
- **키 회전**: 1) 멤버 제거·기기 분실 신고 시 조직 키 즉시 회전(남은 멤버 공개키로 재래핑) 2) 연 1회 정기 회전 3) `key_version` 필드로 이력 관리.
- **키 사용 감사**: 언락 성공·실패, 회전, 내보내기 요청을 감사 로그에 기록(값이 아니라 사건만).

## 2.8 동기화: Google이 보는 것 / 못 보는 것

우리는 서버를 두지 않고 고객의 Google Calendar를 저장소로 쓴다. 따라서 "누가 볼 수 있는가"의 답은 **Google과, 그 캘린더를 공유받은 사람**이다. 이 사실을 기준으로 필드를 설계했다.

| 데이터 | Google이 보는가 | 비고 |
|---|---|---|
| 문서 원본·썸네일 | 해당 없음 | 전송·저장하지 않음 |
| 마스킹된 제목(`[갱신] 유형 · J.K.`) | 봄 | 그래서 마스킹 규칙을 강제 |
| 라이선스 유형·만료일·발급일 | 봄 | 알림·캘린더의 핵심. 민감도 낮음 |
| 발급기관 | 봄 | 필요 시 표시명 축약 |
| 이름(보유자) | 봄 | 설정에 따라 실명/별칭/이니셜, 기본은 이니셜 권장 |
| 라이선스 번호(선택) | **암호문만** | AES-256-GCM, 키는 기기에만 |
| 주민번호·생년월일·주소·전화 | 해당 없음 | 존재하지 않음 |
| 접속 IP·기기 정보 | Google이 처리 | 앱은 수집하지 않음 |

**정직한 한계**: Google Calendar는 종단간 암호화가 아니다. 그래서 (a) 저장 항목을 6개로 줄이고, (b) 제목을 마스킹하고, (c) 번호는 선택+암호화하며, (d) "캘린더에 들어간 정보는 Google 계정 정책을 따른다"고 온보딩에서 고지한다. 우리가 할 수 없는 것을 광고하지 않는다.

## 2.9 "증빙 원본"이라는 약점을 어떻게 메우나

| 요구 | 대응 |
|---|---|
| 실사관이 원본 서류를 요구 | 앱은 "자격 유형·발급일·만료일·번호·보관 위치(예: 사무실 캐비닛 B, 회사 드라이브 경로)"를 제공. 원본은 고객이 이미 가진 저장소에서 제시 |
| 관리자가 사진을 어딘가에 두고 싶어 함 | "촬영 후 내 저장소로 내보내기"(선택): 사용자가 고른 위치(회사 드라이브·파일 앱)로 **한 번 내보내고 앱은 사본을 남기지 않음**. 경로를 레코드의 '보관 위치'에 기록 |
| "나중에 확인하려고" | 선택 기능(v1.1): **문서 지문(해시)** 만 저장. 같은 파일을 다시 대면 "동일 문서"임을 확인할 수 있으나, 해시로 내용을 복원할 수는 없음. 지문도 선택 사항이며 끄면 저장하지 않음 |
| 감사 리포트에 사진이 필요 | 리포트는 **표·상태·이력**으로 구성. 사진이 필요하면 고객이 자기 저장소의 파일을 첨부 (우리는 만들지 않음) |
| 직원이 자기 서류를 잃어버림 | 직원 셀프 화면에서 "내 자격 상태"만 확인. 원본 보관은 회사 정책으로 안내 |

이 설계의 결론: **"증빙 보관 서비스"가 아니라 "자격 레지스트리"로 정의한다.** 제품 소개·약관·영업 자료에서 이 경계를 먼저 밝힌다. 기대를 잘못 잡으면 파일럿에서 가장 큰 불만이 된다.

| 7 | 스캔·추출 | 입력 최소화 | 카메라(가이드) → OCR → 후보 확인 → 유형·카테고리 선택 → 저장. "원본은 저장되지 않습니다" 상시 고지 | 권한 거부 시 수동 입력 |

| 9 | 캘린더 연동 | 캘린더에 올리기 | Google 계정 연결(OAuth), 전용 캘린더 선택/생성, **미리보기(마스킹된 제목·날짜 3건)**, 동기화 켜기, `.ics` 내보내기 대안 | "연동하면 캘린더에서도 1개월·1주·1일 전에 알려드려요" |
| 10 | 실사 리포트 | 감사 대응 | 범위 선택(전체/사업장/근무지/직무/유형) → 미리보기 → PDF(워터마크·마스킹) | "실사 때 이 버튼 하나면 됩니다" |
| 11 | 설정·보안 | 신뢰 | 잠금 방식, 복구 키, 멤버·권한, 감사 로그, 데이터 내보내기/삭제, 연동 관리, "무엇을 저장하지 않는지" 안내 | — |

디자인 원칙: 상태를 색만으로 표시하지 않는다(아이콘+텍스트+D-day). 큰 글씨 모드, 한 손 조작, 오프라인 동작. 촬영 화면에는 **항상** "저장 안 됨" 안내를 고정 노출한다.

## 3.4 OCR·추출 파이프라인

| 단계 | 처리 | 실패 시 |
|---|---|---|
| 1. 촬영 가이드 | 테두리 감지, 기울기 보정, 그림자 경고 | 재촬영 유도(3회 후 수동 입력 제안) |
| 2. 텍스트 인식 | 기기 내 OCR(Apple Vision / Google ML Kit). 서버 전송 없음 | "글자를 못 읽었어요" + 수동 입력 |
| 3. 필드 후보 추출 | 날짜 패턴(MM/DD/YYYY, YYYY-MM-DD, 한글·영문 월), "expires/valid through/만료" 키워드 근접 규칙, 면허번호 패턴 | 후보 없음 → 발급일+유효기간 자동 계산 제안 |
| 4. 사용자 확인 | 후보 1~3개 버튼 제시 → 선택 시 자동 입력. **자동 확정 금지** | 항상 수정 가능 |
| 5. 저장 | 구조화 레코드만 저장. 원본은 이 시점 전에 이미 폐기 | — |
| 6. 안내 | "원본은 저장되지 않았습니다. 필요하면 지금 내 저장소로 내보내세요" | 건너뛰기 가능 |

정확도 목표: 만료일 후보 포함률 85% 이상(표준 자격증·검사 결과지), 오선택 0건(사람 확인 필수). **인식 실패율을 정직하게 계측**한다(성공률 대시보드) — 무저장 구조에서는 "다시 찍기" 비용이 사용자 몫이라 품질이 곧 이탈률이다.

## 3.5 알림 규칙: 기본은 3번, 한 달 · 일주일 · 하루 전

알림은 자격·라이선스마다 **"알림 플랜"** 하나가 붙는다. 기본 플랜은 3단계이고, 각 단계는 시점·채널·수신자를 각각 가진다.

| 단계 | 시점 | 기본 채널 | 기본 수신자 | 문구 예 |
|---|---|---|---|---|
| 1단계 | **D-30**(만료 1개월 전) | 이메일 + 앱 푸시 | 관리자, 보유자(직원) | "OOO님 CPR/BLS가 30일 후 만료됩니다. 갱신 기관 보기" |
| 2단계 | **D-7**(1주 전) | 이메일 + 앱 푸시 | 관리자, 보유자 | "7일 남았습니다. 예약하셨나요? 완료되면 만료일만 입력하면 끝" |
| 3단계 | **D-1**(하루 전) | 이메일 + 앱 푸시 | 관리자, 보유자 | "내일 만료 · 미갱신 시 근무/영업 제한 위험" |
| (선택) 만료 후 | D+1, D+7, 이후 7일마다 | 이메일 | 관리자 | "3일 경과 · 여전히 미갱신" |

**플랜 템플릿**

| 템플릿 | 단계 | 쓰는 곳 |
|---|---|---|
| 기본 3회 | D-30 · D-7 · D-1 | 대부분의 자격·라이선스. **모든 신규 항목의 기본값** |
| 강화 5회 | D-90 · D-60 · D-30 · D-7 · D-1 | 갱신에 예약·교육 이수·서류 발급이 필요한 항목(면허, CPR, 시설 허가) |
| 최소 1회 | D-7 | 이미 다른 채널로 관리 중인 항목, 소음 민감 고객 |
| 커스텀 | 최대 5단계, 1~365일 사이 | 업종·주별 규정에 맞춤. 단계별 채널·수신자 지정 |

**채널과 수신자**

- **앱 푸시(폰 팝업)**: APNs/FCM. 알림을 누르면 해당 라이선스 갱신 입력 화면으로 바로 이동.
- **이메일**: 플랜 단계별 발송. 본문에는 라이선스명·유형·만료일·남은 일수·갱신 링크만 담고, **면허번호·생년월일·문서 이미지는 넣지 않는다.**
- **Google Calendar**: 만료일을 캘린더 이벤트로 동기화하면 같은 3단계를 캘린더의 이메일·팝업 알림으로도 받는다(3.6).
- **수신자 지정**: 관리자(기본), 보유자(직원, 자기 것만), 추가 이메일(예: 오피스 매니저, 대표). 사업장 라이선스는 보유자가 '사업장'이므로 관리자·대표에게 간다.
- **묶음 발송**: 같은 날 여러 건이 터지면 한 통으로 묶는다(직원 20명 × 자격 5개가 동시에 오는 날의 소음 방지). 단, D-1 단계는 묶음에서 빼고 건별로 보낸다.
- **조용한 시간**: 오후 9시~오전 7시(현지). 푸시는 다음 날 오전으로, 이메일은 발송 시각을 오전 8시로 고정.
- **실패 처리**: 이메일 반송·푸시 미도달 시 24시간 후 1회 재시도, 그래도 실패하면 관리자에게 "연락처 확인" 알림.

**설계 원칙**: 알림은 **날짜와 유형만** 알면 동작한다. 그래서 서버가 이메일을 보내는 모드에서도 서버가 아는 것은 "어떤 유형이 언제 만료된다"는 사실과 수신 이메일뿐이고, 직원의 서류·면허번호·사진은 알 필요가 없다. 사진이 없는 구조라 알림 파이프라인이 곧 개인정보 유출 경로가 되지 않는다.

## 3.6 Google Calendar = 중앙 저장소

앱은 자체 서버 없이, 고객의 Google 계정에 만든 **전용 캘린더("자격·컴플라이언스")** 를 단일 저장소로 쓴다. 윈도우·맥·iOS·안드로이드의 모든 클라이언트가 같은 캘린더를 읽고 쓰므로, 어느 기기에서 입력하든 나머지 기기에 즉시 반영된다.

| 항목 | 설계 |
|---|---|
| 캘린더 | 전용 보조 캘린더 생성(색·기본 알림 설정). 소유자는 고객. 앱은 이 캘린더만 읽고 쓴다 |
| 이벤트 = 라이선스 1건 | 만료일 종일 이벤트. 제목은 마스킹(`[갱신] 보험 · ABC Care`), 설명에는 앱 딥링크 1줄 |
| 구조화 데이터 | `extendedProperties.private`에 6개 필드를 키-값으로 저장. 한도는 키 44자·값 1KB·이벤트당 300개/32KB이므로 우리 페이로드(약 200바이트)는 여유가 크다 |
| 필드 키 | `lid`(라이선스 ID), `ltype`, `holder`, `issue`, `expiry`, `issuer`, `num`(선택·암호화), `ver` |
| 라이선스 번호(선택) | 입력하면 **공유 키로 암호화해** payload에 넣는다. 키는 초대 링크/QR로 배포하고 각 기기 키스토어에 보관. 캘린더에는 암호문만 |
| 3단계 알림 구현 | 리마인더 오버라이드는 **최대 4주(40,320분) 전**까지만 가능하다. 그래서 만료 이벤트에 D-7·D-1 오버라이드를 걸고, **D-30 '준비' 이벤트를 별도로 하나 더** 만든다(오전 9시, 0분 알림). 이벤트 2개로 3단계를 모두 커버 |
| 참석자 | 담당 직원·매니저를 참석자로 초대(선택). 수락하면 각자의 캘린더·기기에 이벤트와 알림이 생긴다 |
| 충돌 처리 | `lid` 기준 upsert, `updated` 비교 후 최신 우선(LWW). 동시 입력은 최신 유지, 변경 이력은 기기별 로컬 감사 로그에 남긴다 |
| 삭제 | 이벤트 삭제 = 기록 삭제(Google 휴지통 30일). 앱이 임의로 되살리지 않는다 |
| 오프라인 | 로컬 캐시(SQLCipher)에 읽고 쓰고, 온라인 복귀 시 큐를 반영. `syncToken`으로 증분 동기화 |
| 백업·이전 | 캘린더 내보내기(.ics)로 전체 백업, 다른 Google 계정으로 이전 지원 |
| 한계 | 캘린더는 데이터베이스가 아니다. 집계·검색은 클라이언트에서 하고, 이벤트 1,000건 단위로 성능을 점검한다(직원 30명 × 자격 10건 = 300건 수준은 문제 없음) |

**프라이버시 경계(반드시 지킬 것)**

1. Google로 나가는 것은 **마스킹된 제목·날짜·리마인더·(선택) 암호화된 선택 필드**뿐이다. 사진, 주민번호, 생년월일, 주소, 전화번호는 존재하지 않는다.
2. 캘린더는 **우리 통제 밖 영역**으로 취급한다. 제목·날짜는 Google이 볼 수 있다고 온보딩에서 고지한다(그래서 제목을 마스킹한다).
3. 조직 Google Workspace에서 관리자가 캘린더를 공유·감사할 수 있음을 고객에게 알린다. 마스킹 제목은 그 경우에도 견딜 수 있는 수준이어야 한다.
4. 앱을 지워도 캘린더의 데이터는 남는다(=고객 자산). 반대로 캘린더를 지우면 앱 데이터도 사라진다. 이 사실을 설정 화면에 명시한다.

## 3.7 실사 대응 리포트(이미지 없는 리포트)

| 구성 | 내용 |
|---|---|
| 표지 | 사업장명, 생성일시(현지+UTC), 생성자, 요청 목적(실사/입찰/보험), 대상 인원·자격 수 |
| 요약 | 상태별 건수 표, 만료·누락 목록(가장 먼저), 담당자 연락처 |
| 직원별 표 | 이름·직무·근무지, **자격 유형·카테고리**·발급기관·발급일·만료일·번호(마스킹 옵션), 상태, **원본 보관 위치** |
| 사업장 라이선스 표 | 사업 허가·시설 허가·보험 등 보유자가 사업장인 항목을 별도 섹션으로(발급기관·만료일·담당자) |
| 증빙 안내문 | "본 리포트는 자격 정보의 등록 현황이며, 서류 원본은 사업장 보관 위치에 있습니다." |
| 워터마크 | 모든 페이지에 "조직명 · 생성일시 · 수신자 · 사본" 반투명 반복 |
| 무결성 | 마지막 페이지에 SHA-256 해시·레코드 수("이 리포트의 데이터 대조용") |
| 마스킹 옵션 | 면허번호 끝 4자리, 생년월일, 주소 숨김 |
| 형식 | A4/Letter, 인쇄 여백 최적화, PDF/A 옵션 |

크기: 직원 20명 기준 1~2MB(이미지 없음). 이메일 첨부 가능. **"사진이 없어 가볍고, 그래서 더 안전하다"**를 리포트 첫 페이지에 한 줄로 적는다.

## 3.8 데이터 모델(캘린더 중심, 서버 테이블 없음)

| 계층 | 엔티티 | 필드 | 저장 위치 |
|---|---|---|---|
| 원본 | LicenseEvent | `lid`, `ltype`(카테고리), `holder`(이름/별칭), `issue`, `expiry`, `issuer`, `num`(선택·암호화), `status`, `loc`(원본 보관 위치, 선택) | Google Calendar 이벤트 + `extendedProperties.private` |
| 원본 | ReminderEvent | `lid`, `stage`(D-30/D-7/D-1), 리마인더 오버라이드 | 캘린더 이벤트(만료 + D-30 준비) |
| 로컬 | CalendarRef | `calendarId`, 계정 이메일, `syncToken`, 마지막 동기화 시각 | 기기 SQLCipher |
| 로컬 | LicenseCache | 이벤트 사본 + 정렬·필터용 인덱스(상태·유형·만료일) | 기기 SQLCipher |
| 로컬 | AppSettings | 표시 이름, 이름 마스킹 옵션, 조용한 시간, 알림 기본값 | 기기 SQLCipher |
| 로컬 | AuditLocal | 변경 시각·행위·대상·이전 값 해시 | 기기 SQLCipher(append-only) |

**없는 것이 설계다**: 서버의 Organization·Member·Document·Attachment·Thumbnail 테이블이 없다. 우리가 운영하는 데이터베이스가 없으므로 유출될 중앙 저장소도 없다. 데이터는 고객의 Google 계정 안에 있고, 앱은 그 데이터를 읽고 쓰는 도구다.

## 3.9 MVP에서 빼는 것과 그 이유

- **문서 보관함**: 포지션 훼손. 필요하면 고객 저장소로 내보내기.
- **급여/근태/스케줄**: 통합 HR 제품과 정면 충돌.
- **자격 자동 검증(주 라이선스국 API)**: 주별 API 부재·유료·느림. v2 과제.
- **CEU 강의 중개**: 별도 사업.

# 4. 수익 모델 & 가격 전략

## 4.1 원칙

1. **광고 없음.** 민감 정보를 다루는 앱에 광고 SDK를 넣는 순간 신뢰가 끝난다.
2. **무료로 충분히 쓸 수 있게, 유료는 시간을 아껴주는 쪽으로.** 무료는 10건까지 모든 기본 기능(캘린더 동기화·3단계 알림·광고 없음)을 준다. 돈을 내는 이유는 개수 제한 해제 + **입력 자동화(OCR)** + **리포트 내보내기**다.
3. **플랫 기반 가격.** 인원·좌석 과금 없이 계정당 연 $24. 계산이 필요 없고, 소규모 사업장이 부담 없이 시작한다.
4. **숨은 비용 없음.** 기능을 잘라 여러 단계로 팔지 않는다. Free와 Pro 두 단계뿐.
5. **연 결제 단일 상품.** 월 결제·업셀 컴플라이언스 없음. v2에서 다지점·팀 플랜을 검토한다.

# 5. 아키텍처 · 기술 스택 · 로드맵

## 5.1 한눈에 보는 구조

```
[iOS]  [Android]  [Windows]  [macOS]        ← Flutter 단일 코드베이스
   \      |         |        /
    \     |         |       /   Google Calendar API v3 (OAuth 2.0)
     ▼    ▼         ▼      ▼
   ┌──────────────────────────────┐
   │  고객의 Google Calendar       │  전용 보조 캘린더
   │  "자격·컴플라이언스"          │  = 단일 원본(저장소)
   │  이벤트 = 라이선스 1건        │  6개 필드 + (선택) 암호화 번호
   └──────────────────────────────┘
         │                  │
         │ 리마인더(이메일)  │ 이벤트 동기화
         ▼                  ▼
   Google Calendar 알림   각 기기의 로컬 알림(팝업)
```

- **우리 서버가 없다.** 인증은 Google OAuth, 저장은 고객의 캘린더, 화면은 4개 클라이언트.
- 사진은 어느 단계에서도 디스크·서버에 남지 않는다. OCR은 기기 안에서 끝난다.
- 모든 기기가 같은 캘린더를 보므로, 한 기기에서 입력한 만료일이 나머지 기기와 캘린더 알림에 그대로 반영된다.

## 5.2 네 플랫폼을 한 코드베이스로

| 플랫폼 | 주 입력 | OCR | 알림 | 배포 |
|---|---|---|---|---|
| iOS | 카메라 촬영 | Apple Vision(기기 내) | 로컬 알림 + Google Calendar 앱 | App Store |
| Android | 카메라 촬영 | Google ML Kit(기기 내) | 로컬 알림 + Google Calendar 앱 | Google Play |
| Windows | PDF·이미지 파일 드롭/선택 | Windows.Media.Ocr(기기 내) | Windows 토스트 + 캘린더 웹 | MSIX/설치 파일 직접 배포 |
| macOS | PDF·이미지 파일 드롭/선택 | Vision 프레임워크(기기 내) | 알림 센터 + 캘린더 웹 | 공증(notarized) DMG / Mac App Store |

**Flutter를 1순위로 권장하는 이유**: 4개 플랫폼을 한 코드베이스로 유지(1인 개발에 결정적), 모바일 네이티브 카메라·OCR 플러그인 성숙, 데스크톱에서 파일 드롭 UI를 그대로 구현, PDF 생성 라이브러리 존재. 대안은 React Native(데스크톱은 Windows/macOS 별도 프로젝트 필요) 또는 KMP(러닝커브·UI 재작성 부담).

데스크톱의 정직한 한계: Flutter 카메라 플러그인은 데스크톱을 공식 지원하지 않는다. 그래서 데스크톱은 **파일(사진·PDF) 드롭 + OS OCR** 로 설계하고, 웹캠 촬영은 v1.1 이후 과제로 둔다.

## 5.3 왜 캘린더를 저장소로 쓰는가

| 장점 | 단점·대응 |
|---|---|
| 서버·DB 운영비 0, 유지보수 부담 최소 | 캘린더는 DB가 아니다 → 집계·검색은 클라이언트, 1,000건 단위 성능 점검 |
| 고객이 이미 매일 보는 화면에 만료가 보임 | 이벤트가 지저분해질 수 있음 → 전용 캘린더 분리 + 마스킹 제목 |
| 4개 기기·여러 사람이 같은 데이터를 즉시 공유 | 캘린더는 E2EE가 아님 → 최소 필드 + 마스킹 + 선택 필드 암호화 |
| 알림(이메일·팝업)이 Google 인프라로 자동 발송 | Google 의존 → `.ics` 내보내기·로컬 백업으로 탈출구 확보 |
| 데이터가 고객 자산(이전·백업 자유) | 앱을 지워도 데이터가 남음 → 삭제·이전 UX를 명확히 |

## 5.4 보안·신뢰 구조(요약)

1. **무저장**: 사진·PDF는 메모리에서 OCR 후 즉시 폐기(2.3~2.4).
2. **최소 6필드**: 라이선스 유형, 이름(또는 별칭), 발급일, 만료일, 발급기관, (선택) 번호. 그 외 개인정보 없음.
3. **선택 필드 암호화**: 번호를 입력하면 AES-256-GCM으로 암호화해 캘린더 payload에 넣는다(키는 기기 키스토어, 초대 링크로 공유).
4. **서버 없음**: 우리가 침해당해 유출될 중앙 저장소가 없다.
5. **최소 권한**: Google 권한은 앱이 만든 보조 캘린더 범위로 한정(가능하면 `calendar.app.created`, 불가 시 `calendar.events`).

## 7.2 데이터 스키마 (정확한 필드명·타입)

```dart
enum LicenseCategory {
  businessPermit,       // 사업 허가
  professionalLicense,  // 전문 면허
  insurance,            // 보험
  safetyTraining,       // 안전·보수교육
  facilityPermit,       // 시설 허가
  other,
}

class License {
  final String id;              // uuid v4, 캘린더 이벤트와 1:1
  final LicenseCategory category;
  final String licenseType;     // 예: "CPR/BLS", "Food Handler"
  final String holderName;      // 실명 또는 별칭
  final String holderType;      // 'staff' | 'business'
  final DateTime issueDate;     // 날짜만(UTC 00:00)
  final DateTime expirationDate;// 날짜만(UTC 00:00)
  final String issuer;
  final String? licenseNumber;  // 평문은 메모리에서만. 저장 시 암호화
  final String? locationNote;   // 원본 보관 위치(선택)
  final int schemaVersion;      // 1
}
```

**캘린더 payload**: `extendedProperties.private`의 키-값(문자열). 키는 44자, 값은 1KB 제한을 넘지 않는다.

| 키 | 타입 | 필수 | 규칙 |
|---|---|---|---|
| `lm_v` | string | O | 스키마 버전 `"1"` |
| `lm_app` | string | O | 항상 `"license_manager"` (조회 필터용) |
| `lm_id` | string | O | uuid v4 (36자) |
| `lm_cat` | string | O | enum 이름 (예: `professionalLicense`) |
| `lm_type` | string | O | 1~60자, 개행 금지 |
| `lm_holder` | string | O | 1~60자 |
| `lm_htype` | string | O | `staff` 또는 `business` |
| `lm_issue` | string | O | `YYYY-MM-DD` |
| `lm_exp` | string | O | `YYYY-MM-DD`, `lm_issue` 이상 |
| `lm_issuer` | string | O | 1~80자 |
| `lm_num` | string | - | 암호화 봉투 `v1.<base64url>` (평문 금지) |
| `lm_loc` | string | - | 0~120자 |

**검증 규칙**(저장 전 assert): 위 길이·날짜 형식, `expirationDate >= issueDate`, `id`가 uuid v4, `holderType` 화이트리스트. 위반 시 저장하지 않고 폼에 오류 표시.

## 7.3 암호화 명세

| 항목 | 스펙 |
|---|---|
| 조직 키 | 32바이트 CSPRNG. `flutter_secure_storage` 키 `lm.orgKey.v1`. 초대 시 QR/링크 fragment로만 전달(서버 전송 없음) |
| 필드 키 유도 | `HKDF-SHA256(ikm = orgKey, salt = utf8(licenseId), info = utf8("lm/field/num/v1"))` → 32B |
| 필드 암호화 | AES-256-GCM, 12B 랜덤 nonce, AAD = `utf8("lm:v1:" + licenseId + ":" + expiryDate)` |
| 봉투 형식 | `"v1." + base64url(nonce ‖ ciphertext ‖ tag)` (nonce 12B, tag 16B) |
| 복호화 실패 | `null` 반환 + UI에 "번호를 읽을 수 없음(다른 계정 키)" 표시. 크래시 금지 |
| 로컬 DB 키 | `HKDF-SHA256(orgKey, info = "lm/db/v1")` → SQLCipher raw key(hex). DB 파일에는 키 저장 금지 |
| 키 회전 | `lm.orgKey.v2` 생성 후 신규 쓰기부터 v2, 기존 값은 읽을 때 재암호화(지연 마이그레이션). `keyVersion` 필드로 구분 |
| 금지 | ECB, 고정 IV/nonce, 비밀번호를 키로 직접 사용, 평문 번호를 캘린더·로그·분석에 기록 |

## 7.4 휘발성 OCR 파이프라인(정확한 동작)

```
mobile:  camera.startImageStream(frame)
           → crop/rotate/scale (메모리)
           → ocrEngine.recognize(bytes)          # 플랫폼 채널
           → fieldExtractor.extract(text)        # 날짜·번호·이름 후보
           → UI 확인(사용자 선택)
           → frame.fillRange(0, len, 0); dispose()   # 즉시 폐기
desktop: fileDrop(path) → bytes = readAsBytes()   # 메모리로만
           → ocrEngine.recognize(bytes)
           → fieldExtractor.extract(text)
           → bytes.fillRange(0, len, 0)              # 즉시 폐기
```

**폐기 보장 규칙**
1. `takePicture()`를 쓰는 플러그인은 임시 파일을 만든다 → `finally`에서 반드시 `File(path).delete()`. 가능하면 `startImageStream` 경로만 사용.
2. 사진첩·갤러리에 저장하는 API 호출 금지(`UIImageWriteToSavedPhotosAlbum`, MediaStore insert).
3. 썸네일·프리뷰는 메모리 위젯에만. 디스크 캐시 금지.
4. OCR 입력 바이트·추출 텍스트를 로그·크래시 리포트·분석 이벤트에 넣지 않는다.
5. 모바일은 스캔 화면에서 `FLAG_SECURE`(Android) / 캡처 차단(iOS) 적용.

**필드 추출 규칙(우선순위 순)**

| 대상 | 정규식 예 | 후보 최대 |
|---|---|---|
| 만료일 | `(\d{4})[-./](\d{1,2})[-./](\d{1,2})`, `(\d{1,2})/(\d{1,2})/(\d{2,4})`, 한글 `20\d{2}년\s*\d{1,2}월` | 3 |
| 발급일 | 위와 동일 + "issued", "발급" 근접(±30자) | 2 |
| 번호 | `[A-Z]{1,3}[- ]?\d{3,10}`, `\d{6,12}` | 2 |
| 이름 | 라벨("Name", "성명", "Holder") 뒤 1~30자 | 2 |

후보는 항상 사용자 확인을 거친다. 자동 확정 금지. 인식 실패 시 수동 입력 폼으로 폴백.

| 이벤트 A(만료) | `summary = "[갱신] {typeLabel} · {maskedHolder}"`, `start = expirationDate 09:00`, `end = 09:15`(설정 가능, 기본 09:00), `transparency = "transparent"`, `extendedProperties.private` = 7.2 payload, `reminders.useDefault = false` |
| 이벤트 A 리마인더 | `[{email,10080},{popup,10080},{email,1440},{popup,1440}]` (4개, 허용 최대 5개) |
| 이벤트 B(D-30 준비) | `start = expirationDate - 30일 09:00`, 15분, 같은 payload(읽기 전용 표식 `lm_stage = "d30"`), 리마인더 `[{email,0},{popup,0}]` |
| 3단계 보장 | 30일 전 = 이벤트 B, 7일 전 = A의 10080분, 1일 전 = A의 1440분. **D-30 요청값 43200분은 Calendar API 상한(40320분)을 넘으므로 오버라이드로 넣을 수 없다** → 별도 이벤트로 구현(위 표) |
| 멱등성 | 저장 전 `events.list(privateExtendedProperty="lm_id=<id>")`로 기존 이벤트 조회 → 있으면 `events.patch`, 없으면 `insert` |
| 증분 동기화 | `events.list(calendarId, syncToken, privateExtendedProperty="lm_app=license_manager", showDeleted=true, pageToken)` |
| 토큰 만료 | `410 Gone` → `syncToken` 폐기 후 전체 동기화 |
| 충돌 | 동일 `lm_id`에 대해 `updated`가 더 최신인 쪽 채택(LWW). 로컬 큐에 남은 변경은 재시도 |
| 삭제 | 앱에서 삭제 시 `events.delete`. 외부에서 지워진 이벤트는 로컬에서도 삭제(재생성 금지) |
| 재시도 | 429/5xx → 지수 백오프(1s, 2s, 4s, 최대 5회). 401 → 토큰 갱신 후 1회 재시도 |
| 크기 검사 | payload 직렬화 후 1KB 초과 시 `lm_loc`/`lm_type` 절단 대신 저장 거부 + 오류 표시 |
| 시간대 | 날짜는 `YYYY-MM-DD`(달력 날짜)로 저장, 이벤트 시간은 기기 로컬 09:00 |
